## Что перенесено

- JD: форма с семью разделами, сборка без AI, генерация AI-черновика по введённым данным,
  отдельные внутренние комментарии, сохранение шаблона. Неизвестные условия остаются
  «Требует уточнения». AI не сохраняет и не утверждает документ автоматически.
- Если по утверждённой версии JD уже создана вакансия, отображается ссылка на неё.
  Добавлена страница вакансии с переходом к её откликам; учитывается архив.
- Карточка кандидата: AI-выжимка, цитаты из резюме, таблица критериев, вопросы и процент.
  Ручная оценка и этап не меняются. Полный текст резюме сохранён, показывается 5 строк
  с кнопками «Развернуть»/«Свернуть».
- В списке откликов AI-оценка отдельно от ручной, с мягкими цветами; устаревший результат
  не показывается как актуальный процент. Существующая сортировка остаётся по РУЧНОЙ оценке.
- Формулировки отчётов скорректированы: AI доступен в карточке, но его статистика пока
  не включена в Telegram-отчёт/главный отчёт. Автоматический AI-анализ из бота не добавлен.

Формула AI: (подтверждено + 0.5 × частично) / число учитываемых критериев × 100%.
Обязательные и желательные имеют одинаковый вес. Не относящиеся к работе личные признаки
исключаются по инструкции модели. Процент — показатель подтверждения критериев резюме,
а не вероятность найма. Цитаты проверяются на наличие в исходном тексте; смысловую
корректность вывода всё равно проверяет рекрутер.

Старые функции локального проекта, оставшиеся отдельными этапами переноса:

- шаблоны сообщений и прямая отправка Telegram;

- остальные различия bot.py (не заменять его локальным SQLite-файлом).
В этом обновлении не копируются SQLite-база и её накопленные AI-результаты/заметки.

## PostgreSQL

Существующий init_db при старте выполняет добавочную миграцию под тем же advisory lock:
- job_descriptions.internal_notes TEXT DEFAULT '';
- job_descriptions.template_inputs JSONB DEFAULT '{}';
- candidate_ai_runs с JSONB-результатом, TIMESTAMPTZ датой и BIGINT ссылкой на отклик.
Повторное применение безопасно. Старые JD и их версии не переписываются; legacy PUT
без новых полей сохраняет уже существующие комментарии и шаблон.
Изменений таблиц с ручной оценкой/статусами нет. Перед обычной выкладкой должна быть
актуальная резервная копия PostgreSQL согласно процессу команды.

AI-запуски получают UUID. Захват запуска сериализован pg_advisory_xact_lock между
процессами. Транзакция завершается до сетевого запроса. Снимок входных данных читается
одним SQL-запросом. Устаревание проверяется по fingerprint резюме+вакансии+критериев.
Одинаковый UUID не вызывает повторную оплату; актуальный успешный результат переиспользуется.
Один активный анализ резюме на приложение, пауза 10 секунд между новыми попытками.
Зависший запуск после 180 секунд отображается как неизвестный; повтор только по решению HR.
Генерация JD сохраняет локальную блокировку процесса и паузу, как исходная реализация
(для нескольких API workers её стоит заменить отдельным общим лимитом).

## OpenAI

Используются существующие OPENAI_API_KEY и OPENAI_MODEL в окружении backend;
модель по умолчанию остаётся gpt-4.1-mini. Никаких новых секретов не требуется.
Если ключ был только в старом локальном .env, его наличие на сервере должен проверить
администратор. Не помещать его в Git или NEXT_PUBLIC_*.

Запросы Responses API, text.format json_schema, strict:true, store:false. Автоповторов нет.
Сохранён полный текст резюме как вход анализа, он может содержать контакты внутри текста;
перед отправкой пользователь подтверждает передачу в OpenAI. Отдельные name/contact
поля не отправляются. Внутренние заметки JD не отправляются.
Документация: https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses

## Выполненные проверки

- 8 тестов с PGlite (PostgreSQL в WebAssembly): миграция дважды, JSONB JD,
  сохранение legacy-полей, утверждение, отсутствие сохранения при AI-генерации,
  доступ/согласие, UUID/reuse, stale, ошибка провайдера, отсутствие изменений ручной
  оценки и этапа, отображение карточки/списка, цитаты/формула, формат запросов и store:false.
- UI-тесты: согласие, отсутствие автоматического вызова, нулевой процент красный,
  статус после неизвестного результата, устаревшая оценка и чтение полей JD из JSONB.
- next typegen, TypeScript --noEmit и ESLint перенесённых компонентов — успешно.
- Внешние платные запросы НЕ выполнялись: ответы OpenAI подменены тестовыми.
- Это не проверка инфраструктуры production: PGlite не проверяет psycopg pool/сетевой
  PostgreSQL и многопроцессные блокировки. Полная Next-сборка ограничена текущей средой
  (ENOENT uv_resident_set_memory); сборку выполняет CI команды.

Воспроизвести SQL/API-тесты локально (Node и Python-зависимости backend должны быть установлены):

    npm install --prefix tests/ai_port --no-save --package-lock=false @electric-sql/pglite
    python tests/ai_port/test_port.py -v

Тест использует только новую БД в памяти PGlite, не подключается к DATABASE_URL.

## Проверка после выкладки

1. Войти; без сессии новые API-маршруты должны возвращать 401.
2. JD: заполнить название, цель и задачи; собрать без AI и сохранить. Открыть снова:
   поля шаблона сохранились. Утвердить, создать вакансию и проверить ссылку на неё.
3. С синтетическим резюме открыть карточку кандидата. Проверить раскрытие текста.
4. Дать согласие и выполнить один AI-анализ. Проверить цитаты, процент, отдельность
   от ручной оценки и отображение в списке. Проверить неверный/неполный ответ AI вручную.
5. Изменить критерии тестовой вакансии: предыдущий AI-результат должен стать устаревшим.
6. Проверить /report бота: расписание и сбор данных прежние, изменена только фраза об AI.

Установщик меняет только локальные исходники и создаёт резервные копии. Сайт обновляется
после принятого командой push/deploy. Нельзя заменять серверные файлы SQLite-вариантами.
