# Вход сотрудников в HR Assistant

Основа: архив GitLab, commit 28499d15aa126cf9c0e6f4f31537749c96ba90fa.
Это патч серверной PostgreSQL-версии; не применять к старой SQLite-версии.

## Что реализовано

- Страница /login, логин/пароль, кнопка выхода на страницах кабинета.
- Отдельные учётные записи сотрудников в PostgreSQL. Самостоятельной регистрации нет.
- ВСЕ сотрудники пока имеют одинаковый доступ к ОДНОМУ общему кабинету.
  Не выдавайте такие учётные записи компаниям-клиентам: tenant isolation/роли ещё не реализованы.
- PBKDF2-SHA256, 600000 итераций, индивидуальная случайная соль. Пароли не сохраняются открытым текстом.
- Случайные сессии на 12 часов, в БД только SHA256 токена. Выход отзывает сессию;
  сброс пароля и отключение пользователя отзывают все его сессии.
- Cookie HttpOnly, SameSite=Lax, Secure в production, Path=/, без Domain.
- API принимает пользовательскую авторизацию только через Bearer, не через браузерные cookies.
  Next.js server actions и server reads передают токен в backend. Это защищает API также при обходе proxy.
- Не больше 10 попыток входа на логин за 15 минут; общий предел 60/минуту на приложение.
  Счётчики в PostgreSQL общие для workers. Рекомендуется дополнить ограничением IP на ingress.
- Существующие X-Bot-Key и три разрешённых маршрута бота сохранены.
- /health остаётся публичным; /docs и /openapi.json требуют сессию.
- Добавлены только hr_auth_users, hr_auth_sessions, hr_auth_limits. Таблицы кандидатов не меняются.

## Важное о найденном исходном состоянии

В переданном security.py запрос без X-Bot-Key проходил без авторизации.
Патч закрывает этот путь. Состояние живого сайта отдельно не проверялось.
В deploy/docker-stack.yml обнаружено сопоставление API ${BACK_PUBLISHED_PORT}:8080,
хотя uvicorn запускается на 8000. Патч не меняет публикацию порта; проверьте конфигурацию
прокси команды. Web обращается к http://api:8000 внутри сети Swarm.

## Подготовка и развёртывание (для команды)

1. Ревью отдельной ветки. Не пушить напрямую main: текущий CI автоматически деплоит main,
   а staging также имеет собственный автоматический деплой.
2. Сделать обычную резервную копию PostgreSQL перед выкладкой.
3. Сгенерировать WEB_API_KEY:

   python -c "import secrets; print(secrets.token_urlsafe(48))"

   Записать результат в серверный DOTENV_FILE/хранилище секретов:

   WEB_API_KEY=<сгенерированное значение>

   Один и тот же секрет должен быть доступен API и web. Это НЕ пароль сотрудника.
   Не использовать NEXT_PUBLIC_, не коммитить .env, не отправлять секрет в чат.
   BOT_API_KEY и DATABASE_URL оставить действующими.
   API_INTERNAL_URL для web задан в stack как http://api:8000.
4. Собрать оба образа и выполнить проверки ниже в staging. Без WEB_API_KEY API
   намеренно не стартует. Нельзя выкладывать только frontend или только backend.
5. В контейнере API НОВОЙ версии, имеющем DATABASE_URL, выполнить интерактивно:

   python manage_users.py create kate

   Указать пароль минимум 12 символов, затем повторить. Он не отображается.
   Команда сама создаёт таблицы авторизации; её можно выполнить в одноразовом
   контейнере нового образа до переключения трафика, либо через exec после запуска.
   Имя контейнера/Swarm task определяет администратор инфраструктуры.
6. После согласованной выкладки открыть https://hh.baklajan.io/login и войти.
   Пароль передать пользователю по согласованному защищённому каналу.
   Ingress обязан обслуживать HTTPS и передавать корректные Host/X-Forwarded-Host
   и X-Forwarded-Proto. При ошибке Origin в Server Actions сверить прокси;
   не отключать проверку Origin и не добавлять wildcard trusted origins.

## Управление учётными записями (в контейнере API)

    python manage_users.py create another_user
    python manage_users.py reset-password kate
    python manage_users.py disable kate

reset-password также включает ранее отключённую учётную запись.
Пароли через аргументы командной строки не передаются. Публичной формы восстановления нет.

## Проверки

Локально выполнены:
- 6 unittest-тестов API с изолированной подменой БД: отказ анониму, запрет cookie вместо
  Bearer, проверка секрета входа, неверный пароль, сессия/выход, истечение/отключение,
  лимиты попыток, права бота и Cache-Control; все прошли.
- Next typegen и TypeScript tsc --noEmit прошли.
- Сборка Next (Turbopack и webpack) заблокирована средой проверки:
  ENOENT uv_resident_set_memory. Это не успешная production-сборка.
- Реальный PostgreSQL в среде проверки не запущен. SQL и работу с серверной БД
  необходимо проверить на staging. Тесты с подменой БД этого не заменяют.

Команды:

    python -m unittest discover -s tests -v
    cd web
    npm ci
    npm run build

На staging:
1. Создать тестового сотрудника указанной CLI-командой.
2. В приватном окне / и /applications переводят на /login.
3. Прямой запрос к API /applications без Bearer — 401; /health — 200.
4. Неверный пароль — общее сообщение, верный — вход; проверить Secure/HttpOnly cookie.
5. Открыть вакансии/кандидата/настройки, сохранить тестовую заметку/этап.
6. Выйти: старый токен больше не работает. Сбросить пароль — другие сессии тоже не работают.
7. Проверить /start и /report бота. X-Bot-Key не даёт доступ к настройкам и прочим маршрутам.
8. Неверные пароли 10 раз — дальнейшая попытка ограничена; через 15 минут вход снова доступен.
9. API недоступно — сайт сообщает временную недоступность, не показывает данные.
10. Только после проверок сливать в main.

## Откат

Исходные файлы сохраняет установщик в .auth-login-backups/. Поддерживаемый откат —
реверт коммита вместе с согласованной временной защитой доступа на ingress.
Простой возврат старой версии снова уберёт API-авторизацию: не открывать её публично.
Таблицы hr_auth_* можно оставить — они не меняют старые бизнес-таблицы.
